# RequestOps

Automates the college event-permission workflow: a student submits a request, a coordinator approves or rejects it **inside Notion**, and the system fires a real email + writes a code-attributed audit log — with no manual intervention once deployed.


---

## Architecture

```
Trigger (form submission)
        │
        ▼
  Backend Service (Node.js / Express)
        │
        ▼
  Notion "Requests" DB  ──▶  Page created, Status = Pending
        │
        ▼
  Coordinator reviews & decides inside Notion (Approved / Rejected)
        │
        ▼
  Cron job (every 2 min, runs on its own) detects the decision
        │
        ├─▶ Real Action: email sent
        └─▶ Run Log: row written by code, real timestamp
```

Notion is the **only** human interface. The coordinator never touches code, a terminal, or a separate dashboard — they open the "Requests" database, read what's pending, and change one field.

## Setup

### 1. Install

```bash
npm install
```

### 2. Notion setup

Create an integration at [notion.so/my-integrations](https://notion.so/my-integrations), name it "RequestOps Bot," and copy its **Access token**.

Create two full-page databases in your workspace and connect the integration to **both** (`···` menu → Connections → add "RequestOps Bot").

#### "Requests" database

| Property | Type | Notes |
|---|---|---|
| Request ID | Title | Auto-generated by code, e.g. `REQ-1787812136232` |
| Student Name | Text | |
| Email | Email | Where the decision email is sent |
| Event Name | Text | |
| Event Date | Date | |
| Venue | Text | |
| Description | Text | Raw free-text from the student |
| Status | Select — options: `Pending`, `Approved`, `Rejected` | The human approval gate |
| Decision Reason | Text | **Coordinator-owned.** Code reads this, never writes it. |
| Processed At | Date | Set by code once the real action has fired — acts as the "already handled" lock |

#### "Run Log" database

| Property | Type | Notes |
|---|---|---|
| Run ID | Title | Auto-generated, e.g. `RUN-1787812185830` |
| Request ID | Text | Correlates back to the originating request |
| Status | Select — options: `Created`, `Success`, `Failed` | |
| Timestamp | Date (with time) | Written by code at execution time — never typed by hand |
| Outcome | Text | Human-readable description of what happened |
| Error | Text | Populated only on failure |

### 3. Environment variables

Create a `.env` file in the project root (already gitignored):

```
NOTION_TOKEN=your_integration_token
REQUESTS_DATABASE_ID=your_requests_database_id
RUN_LOG_DATABASE_ID=your_run_log_database_id
PORT=3000
```

Database IDs come from each database's URL: `notion.so/yourworkspace/<DATABASE_ID>?v=...`.

### 4. Run it

```bash
node src/server.js
```

You should see:
```
[cron] scheduled to check every 2 minutes
Server running on http://localhost:3000
```

These exist for testing without a real form yet — safe to keep during the hackathon, remove before final submission if you want a cleaner surface.

| Route | What it does |
|---|---|
| `GET /` | Health check |
| `GET /test-create` | Creates one hardcoded test request in Notion, status `Pending` |
| `GET /test-decided` | Returns every request the coordinator has decided on but the system hasn't processed yet |
| `GET /test-process` | Manually triggers `processDecisions()` immediately, instead of waiting for the cron tick |

**Normal test loop:** hit `/test-create` → change that row's Status in Notion → either wait ≤2 minutes for cron, or hit `/test-process` to trigger it immediately → check your terminal for the `[email:MOCK]` line and Notion's Run Log for the new row.

## How this maps to the judging criteria

- **Runs without manual intervention** — `cron.schedule("*/2 * * * *", ...)` in `src/server.js` checks Notion on its own; nothing requires a human to run a script or visit a URL.
- **Real human approval gate** — the coordinator's only action is changing `Status` inside the actual "Requests" database. The email genuinely does not send until after that change is detected.
- **Code-written, timestamped Run Log** — every row in `createRunLog()` (`src/notion.js`) is created by the integration with a real `new Date().toISOString()` timestamp, never typed by hand.
- **Decision Reason is coordinator-owned** — code only ever *reads* this field (`getText(page, "Decision Reason")`); it is never overwritten by the processor, so a rejection reason typed by a human survives all the way into the email.
- **Idempotency** — `getDecidedRequests()` filters out anything where `Processed At` is already set, and `markProcessed()` is only called after the real action succeeds — so a failed email retries on the next cron tick instead of being silently marked done.
- **Delete-the-repo test** — with this backend not running, nothing in Notion changes automatically: no emails send, no Run Log rows appear. The logic lives entirely in this code, not in a no-code layer sitting on top of Notion.
- **Backend-off test** — the Notion "Requests" database remains a fully readable, human-operable table on its own — a coordinator can always see what's pending, approved, or rejected, with or without this server running.
